# 方案：打印体系（模板登记 + 批量出证书 + 打印留痕 + 文档索引）

> 版本：v9（待评审）
> 日期：2026-09-30
> 状态：方案阶段，未开始实施
> 定位：**个人本地单机使用**（不涉及多端协作 / 云端）

> **v9 修订（模板登记方式定案）**：用户明确 ——
> **「模板登记方式：按照上传底图 + 需要替换的字段。而替换的字段，可以由用户勾选，
> 它的完整集合来源于工作台的数据库表。」**
>
> 据此调整：
> - **模板登记 = 底图 + 勾选字段**；不再要求登记设计稿文件（`source_path` 降为可选）
> - **字段目录来自数据库表的列**，用户**勾选**（不再让用户手写字段名）
>   —— 天然绑定数据、不会拼错、系统知道类型（§7.3.6）
> - 表结构：`background` 变 NOT NULL、删掉 `fill_mode`、`fields` 改为 `{column, label, x, y, …}`
> - 新增接口 `GET /api/print/fields`（字段目录）

> **v8**：立「不越权」产品原则（§1.1）；删掉「项目打印信息」中间层（§5.5）；
> 收回"别造太多模板"的规劝。
> **v7**：尺寸从图片自动读取；坐标存百分比（底图换分辨率不错位）。
> **v6**：生成载体用 HTML，只复刻「文字层」（底图 + 叠字），消掉 docx 的 run 分割坑。
> **v5**：命名占位符（按名字匹配），不用「按位置识别横线」。
> **v4**：工作台只做「模板路径汇聚、索引、一键打开」，样式与编辑交给专业软件。

## 1. 要解决的问题

证书台账是全项目**最完整**的模块（编号规则、批量导入、按收件机构分组导出 xlsx、`packed` 打包核对字段齐备），
但它止步于 **Excel 台账** —— 系统里没有任何「能打印/能寄出去的文档本体」。

同时存在一个未被覆盖的需求：

> 几百张证书寄出去之后，**回头对不上账**。谁在什么时候打印了哪一批？现在完全没有记录。

本方案做三件事，按依赖顺序：

1. **打印产出**：让「打印」这件事发生在工作台内部（证书、清单、报表）
2. **打印留痕**：每次打印自动记录（类型 / 时间 / 关联实体 / 文档快照）
3. **文档索引**：给这些文档建全文索引，支持跨系统搜索

> 第 1 步是前提。**没有它，后两步无处附着** —— 详见 §3.1。

### 1.1 产品原则：做平台与半自动化，不越权

用户明确定位：**「我们做平台和半自动化设计，不要越权。」**

这条原则贯穿全案，具体表现为：

| 归系统（平台能力） | 归用户（业务决策） |
|---|---|
| 上传底图、读尺寸、建议纸张 | 底图长什么样、用什么软件设计 |
| **列出数据库有哪些列**（客观事实） | **勾哪些列作为字段** |
| 字段定位、替换、循环生成、打印 | 排在什么位置、什么字号、什么颜色 |
| 归档、留痕、索引 | **建几个模板**、怎么组织、给哪个项目用 |

**具体到本方案，系统刻意不做这些事**：

- ❌ **不替用户决定用哪些字段** —— 字段目录来自数据库表（客观事实），勾哪些是用户的决定
- ❌ **不规定一届活动该有几类证书** —— 这是用户的业务决策
- ❌ **不规定模板该按什么维度组织** —— 系统提供归属维度能力，用不用、怎么用由用户决定
- ❌ **不追求全自动** —— 半自动化即可：系统做能做的（替换、循环、打印），剩下的交给用户

> 这条原则的直接后果：方案比 v3 少了**两个中间层**（自研渲染引擎、项目打印信息字段）。
> **"不越权"往往同时意味着"更简单"。**

## 2. 现状盘点

### 已有，可直接复用

| 能力 | 位置 | 复用来做什么 |
|---|---|---|
| 证书台账数据 | `certificates` 表（含 cert_number / award / work_name / instructor / cert_number 等） | 打印数据源 |

| 按机构分组 | `certificateExport.js` 的 `groupByReceivingOrg()` | 打印分组依据 |
| 文档文本提取 | `server/system/routes.py` 的 `_extract_text()`（txt/docx/pdf） | **全文索引的提取器** |
| 归档分类权威定义 | `server/archive/taxonomy.py` | 新增打印归档分类 |
| 模板管理 | `templates` 表 + `TemplatesView.vue` | 参考其管理交互 |

### 缺口（已实测确认）

| 缺口 | 证据 |
|---|---|
| **完全没有打印能力** | `window.print` / `@media print` / "打印" 在 `src/` 全库**零命中** |
| 无打印留痕 | `certificates.packed` 只有"是否打包"标记，无时间/批次/操作人 |
| 全局搜索不搜文件内容 | `search/routes.py` 只遍历数据库记录，不碰文件 |
| 全局搜索性能差 | 在 Python 内存里遍历全表（每次 `get_all()`） |

### 技术前提（已实测，决定方案选型）

```
SQLite 版本：3.53.1
FTS5 基础支持：可用
FTS5 trigram 分词器：可用
```

中文检索实测（原文「全国展演金奖获奖证书张三」）：

| 查询 | trigram | LIKE | 结论 |
|---|---|---|---|
| `获奖证书`（4 字） | ✅ 1 | 1 | trigram 可用 |
| `全国展演`（4 字） | ✅ 1 | 1 | 任意位置子串都命中 |
| `展演`（2 字） | ❌ 0 | 1 | **trigram 对 2 字词完全失效** |
| `张三`（2 字） | ❌ 0 | 1 | 同上 |

> ⚠️ **这个细节必须实测才知道**：trigram 以 3 字符为最小单元，
> 中文两字词（"展演""金奖""张三"）在 trigram 下**恒为 0 结果**。
> 若直接上 trigram 而不做回退，用户搜两字词会以为"系统里没有"，属于静默失效。

## 3. 关键设计决策

三个决策都会直接影响实现，先把取舍摆明。

### 3.1 决策一：「自动收藏打印过的文档」只有在打印由工作台发起时才成立

```
用户点了「打印」
   ├─ 打印由工作台发起   → 系统掌握文档本体 + 类型 + 时间 + 关联实体 → 可真正自动收藏
   └─ 在 Word/Excel 打印 → 打印队列只能读到 文档名/页数/时间 → 只能留痕，拿不到本体
```

**技术边界（必须诚实说明）**：Windows 打印队列拿到的是 EMF 假脱机数据，**还原成可读文档不可靠**。
因此「拦截系统打印 → 收藏文档本体」这条路走不通。

**推论**：

- 本功能**不能做成独立软件** —— 独立软件无法解决"怎么知道打印了什么"，也拿不到内容；
- 做进工作台后，元数据（类型 / 时间 / 关联的项目·选手·机构）**全部是现成的**，边际成本几乎为零；
- 所以它**排在证书套打之后**，是打印体系的自然延伸，不是并列的独立功能。

### 3.2 决策二：文档本体怎么拿 —— 生成本身在工作台内，归档顺理成章

> ⚠️ **v4 带来的连带后果（诚实说明）**：
> v1–v3 里工作台自己渲染打印稿，所以天然拿得到文档本体。
> **v4 曾把生成交给 Word/Excel**，于是"自动归档文档本体"不再免费。
> **v6 又把它拿回工作台**（用 HTML 生成）—— 这个问题随之解决。

**v6 定案：生成本身就在工作台内完成，归档是顺手的**

| 填充方案 | 工作台能否拿到文档本体 | 归档能力 |
|---|---|---|
| 邮件合并（备选） | ❌ 生成发生在 Word 里 | 只能留痕；需"约定目录 + 扫描"补救 |
| **HTML 生成（v6 采用）** | ✅ 工作台自己生成 | **生成即归档，闭环完整** |

**归档格式：生成的 HTML** —— 理由：

1. **可再打印**：打开就是打印预览，直接重印或另存 PDF
2. **文本可直接抽取建索引**：HTML 抽文本比 docx / PDF 都容易（§9 的全文搜索直接受益）
3. **体积极小**：一个批次几百页也就几百 KB
4. **零依赖**：不需要 PDF 库

**注意**：归档的 HTML 里**底图是引用路径**，不是内嵌 base64 ——
否则一个批次文件会膨胀到几十 MB。归档时需保证底图仍在原位置（底图放素材库，纳入备份范围）。

> 若将来确实需要"PDF 本体"（比如要发给别人），从归档 HTML 打印时选"另存为 PDF"即可，
> 不必为此引入 PDF 生成库。

### 3.3 决策三：打印归档不违反「一份文档一个家」

`server/archive/taxonomy.py` 开头明确要求避免「同一份文档有多个家」。这里要区分两件事：

| | 说明 | 是否冲突 |
|---|---|---|
| 张三的获奖证书 | 已存在于 `02_选手档案/张三/04_获奖证书/` | — |
| **一次打印批次**（如"9/30 打印了 20 张省赛证书"） | 这是**新产生的文档**（一个批次文件），不是已有文档的副本 | **不冲突** |

打印批次天然是**批次级产物**，无法塞进某个人的目录（它跨多个实体）。
因此物理上单独归档，但**元数据里记录关联实体**，实体页可反查"这个人的证书被打印过几次"。

```
MediaArt_Archives/
  07_打印归档/                    ← 新增一级分类（taxonomy 权威定义）
    证书/2026-09/2026-09-30_1430_省赛证书_20份.html
    清单/2026-09/2026-09-30_1445_选手报名清单.html
```

```
└────────────────────┬─────────────────────────────────────┘
                     │ 工作台只登记「路径 + 元数据」

│  ① 扫描约定目录自动登记   ② 记录 file_mtime（看出被改过）   │
│  ③ 按 名称/类型/项目·年份 索引                             │
└────────────────────┬─────────────────────────────────────┘
                     │
        ┌────────────┴────────────┐
        ▼                         ▼
┌───────────────────┐   ┌────────────────────────────────┐
│ 一键打开           │   │ 批量生成（HTML）                │
│ /api/open-file    │   │ 底图(Word导出) + HTML 叠字      │
│ → os.startfile    │   │ {{选手姓名}} 按名字替换          │
│ 改完存盘即见       │   │ 一份含 N 页 → 浏览器打印/存PDF   │
└───────────────────┘   └────────────┬───────────────────┘
                                     │ 扫描归档目录 + 留痕
                     ┌───────────────┴───────────────┐
                     ▼                               ▼
             ①打印留痕 print_logs           ②全文索引 doc_index
             谁·何时·哪批·用哪个模板          FTS5 trigram + 2字回退
                     └───────────────┬───────────────┘
                                     ▼
┌──────────────────────────────────────────────────────────┐
│  统一搜索：跨「数据库记录 + 打印文档」                      │
│  结果按 类型 / 时间 聚合展示（索引维度，非物理目录）          │
```

**与 v3 的关键差别**：工作台**从"渲染器"退成"登记 + 索引 + 打开 + 填充"**。
不写渲染引擎、不做可视化编辑器、不维护毫米坐标 —— 这些全部交给专业软件。

## 5. 数据模型

### 5.1 模板登记表（新增）

> ⚠️ **模板登记 = 「底图 + 勾选的替换字段」**（用户明确的设计）。
> 底图承载所有固定内容，字段承载所有变化内容 —— 不需要登记设计稿文件。

```sql
CREATE TABLE IF NOT EXISTS print_templates (
    id            TEXT PRIMARY KEY,
    name          TEXT NOT NULL,        -- 「2026 全国展演获奖证书」
    doc_type      TEXT NOT NULL,        -- 'certificate' | 'roster' | 'report'

    -- ---- 底图（模板的主体）----
    background    TEXT NOT NULL,        -- 底图路径（用户上传的 PNG/JPG）
    page_width    REAL,                 -- 底图像素宽（自动读取）
    page_height   REAL,                 -- 底图像素高（自动读取）
    page_size     TEXT,                 -- 'A4-landscape' | 'A4-portrait' | 'A3-…' | 'custom'

    -- ---- 替换字段（用户从数据库表字段中勾选，见 §7.3.6）----
    fields        TEXT,                 -- JSON：[{column, label, x, y, fontSize, align, color}]

    -- ---- 归属维度（全部可空 = 通用模板）----
    project_id    TEXT,                 -- 绑定到具体项目
    cert_round    TEXT,                 -- '省级展演' | '全国展演'
    year          TEXT,                 -- '2026'（年限演进用）

    -- ---- 可选：设计稿源文件（想从工作台一键打开设计软件时登记）----
    source_path   TEXT,                 -- templates/证书/2026全国展演.psd（可空）
    source_ext    TEXT,                 -- psd / docx / ai …（决定用哪个软件打开）
    source_mtime  TEXT,                 -- 源文件最后修改时间

    note          TEXT,
    created_at    TEXT,
    updated_at    TEXT
);

CREATE INDEX IF NOT EXISTS idx_print_tpl_scope
    ON print_templates(doc_type, project_id, cert_round, year);
```

**v9 相对 v8 的变化**：

| 变化 | 原因 |
|---|---|
| `background` 变 **NOT NULL** | 模板的主体就是底图（用户设计） |
| 删掉 `fill_mode` | 只有 HTML 一种生成方式了，不需要开关 |
| `file_path` 等 → 降为**可选**的 `source_path` | 模板登记不再要求源文件；但 v4 确认过"一键打开设计稿"的体验，故保留为可选 |
| `fields` 结构改为 **`{column, label, x, y, …}`** | `column` 指向数据库表的列（用户勾选而来），`label` 仅用于界面显示 |

**关于 `fields` 里的坐标** —— 这里与 v4 不矛盾，要区分清楚：

| | 归谁 | 说明 |
|---|---|---|
| **版式**（花纹、边框、艺术字、位置关系） | **底图**（用户上传） | 工作台不定义、不渲染 |
| **字段落点**（姓名打在图上哪个位置） | 工作台的 `fields` | 只是一组坐标，用于把文字叠到图上 |

也就是说：工作台**不做排版**，只记录"文字贴在底图的哪里"。
定位工作由 §7.3.4 的字段定位器一次性完成。

**`fields` 的结构（勾选自数据库表 + 定位）**：

```json
[
  {
    "column": "player_name",
    "label": "选手姓名",
    "x": 42.5, "y": 38.2,
    "fontSize": 26, "align": "center", "color": "#1a1a1a"
  },
  {
    "column": "award",
    "label": "奖项",
    "x": 42.5, "y": 55.0,
    "fontSize": 20, "align": "center", "color": "#1a1a1a"
  },
  {
    "column": "cert_number",
    "label": "证书编号",
    "x": 88.0, "y": 92.0,
    "fontSize": 11, "align": "right", "color": "#666666"
  }
]
```

| 键 | 说明 |
|---|---|
| `column` | **数据库表的列名** —— 数据从哪来（用户勾选时确定，不由用户手写） |
| `label` | 界面显示名（默认取列的中文标签，可改，**仅影响显示**） |
| `x` / `y` | 位置，**百分比**（相对底图，换分辨率不错位，§7.3.3） |
| `fontSize` / `align` / `color` | 文字样式 |

**为什么 `column` 比"用户自己起字段名"更好**：

| | 用户自定义字段名 | **勾选数据库表列** |
|---|---|---|
| 数据绑定 | 需要额外建立"字段名 → 数据源"映射，可能配错 | **天然绑定**，列就是数据源 |
| 拼写 | 可能写错导致取不到值 | **勾选，不会拼错** |
| 类型 | 系统不知道 | 系统知道（可做格式校验） |

> **注意**：这不违背 §1.1「不越权」——
> 系统提供的是**"数据库里有哪些列"这个客观事实**（它自己的数据结构），
> 至于**勾哪些、怎么排布、字体多大**，全部由用户决定。

**为什么不用现有 `templates` 表**：那张表是「合同/表单」的内容模板，
语义是"往文档里填内容"；而这里登记的是**底图 + 字段定位**。**刻意分表**。

**底图放哪**：沿用现有素材库路径规范（`resources/` 下），纳入备份范围。

### 5.2 打印留痕（新增）

```sql
CREATE TABLE IF NOT EXISTS print_logs (
    id           TEXT PRIMARY KEY,
    doc_type     TEXT NOT NULL,         -- 'certificate' | 'roster' | 'report'
    title        TEXT NOT NULL,         -- 「省赛获奖证书」
    template_id  TEXT,                  -- 当时用的模板（可能已被改/被删）
    template_snapshot TEXT,             -- ⭐ 当时的模板定义快照（JSON，见下方说明）
    entity_type  TEXT,                  -- 'project' | 'player' | 'org'
    entity_id    TEXT,
    entity_name  TEXT,
    item_count   INTEGER DEFAULT 0,     -- 本批包含多少份（如 20 张证书）
    ref_ids      TEXT,                  -- JSON：涉及的证书编号 / 选手 id
    snapshot_path TEXT,                 -- 归档中的生成文档相对路径（如 .docx）
    printed_by   TEXT,
    printed_at   TEXT,
    ip_address   TEXT
);

CREATE INDEX IF NOT EXISTS idx_print_logs_time ON print_logs(printed_at DESC);
CREATE INDEX IF NOT EXISTS idx_print_logs_entity ON print_logs(entity_type, entity_id);
CREATE INDEX IF NOT EXISTS idx_print_logs_type ON print_logs(doc_type);
```

**为什么留痕里要存 `template_snapshot`**（针对"年限变化"的关键设计）：

模板是会演进的 —— 2026 年把版式改了，但 2025 年那批证书**当初是按老版式打的**。
如果留痕只存 `template_id`，将来点「重印」会拿**新版式**重排历史批次，
打出来的东西和当初寄出去的不一致 —— 这对"对账"是致命的。

存一份当时的模板定义（几 KB 的 JSON），换来：

- 模板**随便改、随便删**，历史批次永远能**原样重印**
- 不需要维护复杂的版本链
- 重印时可直接对比"这批当时用的是哪版版式"

代价只有一个字段的空间，**非常划算**。

### 5.3 文档全文索引（新增）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS doc_index USING fts5(
    doc_id      UNINDEXED,   -- 对应 print_logs.id
    title,
    doc_type,
    entity_name,
    body,                    -- 从生成文档抽取出的纯文本
    tokenize = 'trigram'
);
```

### 5.4 与全量快照的关系

`print_templates` 由用户在工作台里编辑 → **纳入** `POST /api/data/save` 快照。
`print_logs` 与 `doc_index` 由服务端在打印时写入 → **不纳入**快照
（与 `submit_links` 同理：服务端独占写入的数据不能被前端整体覆盖）。

### 5.5 不需要「项目打印信息」字段（v8 删除）

v3–v7 曾计划给 `projects` 加一个 `print_meta` 字段（赛事全称 / 主办单位 / Logo / 届次），
作为填充数据的取值来源。**v8 删除这个设计** —— 用户指出它已被「底图 + 动态字段」覆盖：

| 内容 | 归哪 |
|---|---|
| Logo、花纹、主办单位名称等**固定内容** | **底图**（直接画在图上） |
| 选手姓名、奖项、证书编号等**变化内容** | **动态字段**（用户自定义） |
| 若某项"整批相同但会变"（如今年换了主办方） | 做成**动态字段**，打印时填一次 |

**结论**：不需要在项目表上再挂一层结构化文案。
底图承载"不变"，动态字段承载"变"，**没有中间层**。

> 这是本方案第三次因为"少做一层"而变简单（v4 砍自研引擎、v6 换 HTML、v8 删项目字段）。
> 值得记住：**中间层往往是可以省的**。

## 6. 接口设计

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/print/templates` | 登录 | 模板列表 |
| POST | `/api/print/templates` | `settings:edit` | 登记 / 更新模板（底图 + 勾选字段 + 归属） |
| DELETE | `/api/print/templates/<id>` | `settings:edit` | 删除模板 |
| GET | `/api/print/fields` | `projects:view` | **字段目录**：可用字段清单（来自数据库表的列 + 中文标签） |
| POST | `/api/print/background` | `settings:edit` | 上传底图 → 返回**像素尺寸 + 建议纸张**（§7.3.3） |
| POST | `/api/print/open` | `projects:view` | （可选）一键打开设计稿源文件（`os.startfile`）—— 仅登记了 `source_path` 时可用 |
| POST | `/api/print/generate` | `projects:view` | **批量生成**：底图 + HTML 叠字 → 返回可打印的 HTML（含 N 页） |
| POST | `/api/print/archive` | `projects:view` | 把生成的 HTML 落盘到 `07_打印归档/` 并写留痕 + 建索引 |
| GET | `/api/print/logs` | 登录 | 打印记录（按时间倒序，可筛选类型 / 实体） |
| GET | `/api/print/doc/<log_id>` | 登录 | 取回归档文档（用于再打印 / 预览） |
| GET | `/api/search/docs?q=` | 登录 | 文档全文搜索（trigram + 2 字回退） |

**核心流程（三个接口串起来）**：

```
① POST /api/print/generate
   入参：证书 id 列表 + 模板 id
   出参：可打印的 HTML（含 N 页，底图 + 已替换的字段）
   前端收到后直接 window.print()，或用户先预览

② POST /api/print/archive（可选，生成后顺手调用）
   把这份 HTML 落盘到 07_打印归档/<类型>/<年-月>/
   同时写 print_logs（谁·何时·哪批·用哪个模板）+ 抽文本进 doc_index
```

**v6 后的接口变化**：

- **去掉了 `/api/print/render`** —— 工作台不再渲染"版式"，只叠文字层
- **`/api/print/generate` 成为核心** —— 底图 + HTML 叠字，一次产出整批
- **`/api/print/open`** —— 一键打开设计稿（编辑时用）
- **`/api/print/commit` 可省去** —— 因为生成本身就在工作台内完成，
  不再需要"扫描用户另存的文档再配对"（这是 v4 遗留的妥协方案）
- `/api/print/export` 降级为备选（邮件合并路线才需要）

> v6 的一个额外好处：**归档不再依赖"用户自觉另存到约定目录"**。
> 生成即归档，闭环更紧。

**失败处理**：归档失败不阻断生成与打印 —— 打印是用户的当务之急；
但要在记录上标明"本体未归档"，避免"以为存了其实没存"。

## 7. 模板机制：登记 · 索引 · 一键打开 · 批量填充

> **架构原则（v4）**：工作台**不做排版**。
> 模板是磁盘上的真实文件，样式与编辑交给专业软件（Word / Excel / PS…）；
> 工作台负责四件事：**登记路径 → 索引 → 一键打开 → 批量填充数据**。

### 7.1 分工边界

| 环节 | 归谁 | 说明 |
|---|---|---|
| 版式设计、字体、底图、艺术字 | **专业软件** | Word / Excel 的能力上限远超自研引擎 |
| 模板文件存放 | 磁盘（约定目录） | 工作台可扫描登记 |
| 模板索引（名称 / 类型 / 归属 / 修改时间） | **工作台** | 让你找得到、知道哪份是新的 |
| 一键打开 | **工作台** | 调系统默认程序，体验不断（**已有能力**） |
| 数据填充（批量生成） | **工作台** | 见 §7.3 —— 唯一需要补的环节 |
| 打印留痕 | **工作台** | 不变（§5.2） |

### 7.2 索引与一键打开

**登记方式**：

- 扫描约定目录（如 `templates/证书/`）自动登记
- 也支持手动添加任意路径的文件

**登记时读取 `file_mtime`** —— 这一点很重要：
模板是在外部软件里改的，**工作台必须能看出"这份被改过了"**，否则会出现
"我明明改了模板，打出来还是老样子"的困惑。列表上应标记「已更新」并显示修改时间。

**索引维度**：名称 / 文档类型 / 归属（项目 · 赛段 · 年份）/ 文件类型 / 修改时间

**一键打开**：复用已有能力（`/api/open-file` → `os.startfile`），按扩展名交给系统默认程序。
用户改完存盘，回工作台刷新即见。

> 这一层**没有新技术风险** —— 打开文件、扫描目录、读元数据全是现成能力。

### 7.3 批量填充：HTML 承载生成，底图承载版式

「索引 + 打开」解决的是**编辑**；核心需求是**从台账批量生成 200 张证书**，
不能靠手工在 Word 里改 200 遍。

#### 7.3.1 为什么用 HTML 做「生成载体」

用户提出：**把最终要打印的模板用 HTML 呈现，方便脚本替换与自动循环**。
这个判断是对的 —— HTML 在**生成 + 打印**环节全面优于 docx：

| 环节 | docx 模板 | **HTML 模板** |
|---|---|---|
| 字段替换 | **run 分割坑**（Word 会把 `{{姓名}}` 拆成多个 XML 片段，简单替换必然失败） | **纯字符串替换，没有坑** |
| 循环复制 | 要复制 XML 段落块 | **复制 HTML 块即可** |
| 打印 | 需经 Word | **浏览器直接打印 / 另存 PDF** |
| 建索引 | zip + XML 抽取 | **文本直接可用** |
| 依赖 | 需处理 OOXML | 零新增依赖 |

> **这一条直接消掉了本方案最大的技术风险**（§7.3.5 原先列的 run 分割问题）。

#### 7.3.2 但「复刻」的范围要收窄：只复刻「文字层」

如果要求把**整个版式**（花纹、边框、艺术字、渐变）都用 HTML 复刻，代价很大：
门槛高、难以像素级保真、且和 Word 里的设计**重复劳动两遍**。

**正确做法：把 Word 设计稿导出成图片当底图，HTML 只负责在图上叠加字段文字。**

```
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│    底图       │ + │   文字层      │ = │    成品       │
│ Word 导出图片 │   │ HTML 绝对定位 │   │ 浏览器打印    │
│ 花纹边框都在图上│   │ {{选手姓名}}  │   │ 一份含 N 页   │
│ 版式 100% 保真 │   │ 纯字符串替换  │   │ 一次打完整批  │
└──────────────┘   └──────────────┘   └──────────────┘
```

**关键：复刻的只是「文字层」，不是整个版式。**
你仍然只用 Word 设计（v4 原则不变），系统只需要知道**「字段打在图上哪个位置」**。

这样 v4 与本次设想就**合并**了：

| 职责 | 归属 |
|---|---|
| 版式设计（花纹 / 边框 / 艺术字） | **Word**（导出成底图） |
| 字段定位 + 替换 + 循环 + 打印 | **HTML** |

#### 7.3.3 尺寸与坐标系：从图片自动获取，坐标存百分比

> 用户提出：「把 PS 的图作为 HTML 的背景图，**盒子的大小根据图片的真实尺寸自动获取和调整适配**」。
> 这个补充是对的 —— 尺寸绝不能硬编码。

**① 自动读取图片像素尺寸（已实测，纯标准库零依赖）**

不需要 Pillow。读文件头即可：

| 格式 | 方法 | 实测结果 |
|---|---|---|
| PNG | 8 字节签名 + IHDR，宽高是 big-endian uint32 | ✅ 128×128 / 16×16 全对 |
| JPEG | 扫描段找 SOF0–SOF15（排除 DHT / JPG / DAC） | ✅ 1920×1200 对上 |

约 40 行代码，放在 `server/` 的工具模块里。

**② 从像素尺寸自动建议纸张**

像素是"图"，打印是"物理尺寸"，中间需要桥接。**不让用户手填，而是自动建议**：

```
上传 3508×2480  →  宽高比 1.414  →  建议「A4 横向」  →  用户确认即可
上传 2480×3508  →  宽高比 0.707  →  建议「A4 纵向」
上传 4961×3508  →  宽高比 1.414  →  建议「A3 横向」
```

用户只需**点一下确认**，不需要输入任何尺寸数字。特殊尺寸可选手动指定。

**③ 坐标系：位置存「百分比」，不存「像素」** ⭐

这是本设计里最容易被忽略、但后果最严重的一条：

| 坐标单位 | 底图换分辨率后 | 说明 |
|---|---|---|
| 像素（`x: 1480px`） | ❌ **全部错位** | 3508px 的图导出成 1754px，坐标全废 |
| **百分比（`x: 42.5%`）** | ✅ **不受影响** | 相对底图，永远对得上 |

**位置用百分比（相对底图宽高），字号用 pt（印刷单位，打印稳定）。**

好处：你重新导出底图（换了分辨率、换了设计软件）时，**字段位置不会错位**，不用重新定位。

**④ 必须校验：图片宽高比 ≠ 纸张宽高比 → 拉伸变形**

底图是 3508×2480（A4 横比例 1.414），若误选 A4 竖（比例 0.707），
图片会被拉成竖版 —— **整张证书变形**。所以上传时要**比对比例并明确提示**：

```
⚠️ 底图比例 1.414 与所选纸张比例 0.707 不一致，会导致图片变形。
   建议改用「A4 横向」，或选择「按图片比例自定义纸张」。
```

**⑤ 打印时提醒「缩放 100%」**

浏览器打印对话框若缩放不是 100%，输出会整体偏移。
打印预览页顶部要有明确提示 —— 这是实际打印最常见的坑。

#### 7.3.4 字段定位器

工具做两件事：**① 从数据库字段里勾选；② 把勾中的字段在底图上拖到正确位置。**
比 v1–v3 设想的"完整可视化编辑器"（字体 / 颜色 / 对齐 / 多字段管理）**简单得多**。

```
┌─ ① 勾选字段（来自数据库）────┐ ┌─ ② 定位 ──────────────────┐
│ [x] 选手姓名  player_name    │ │ [上传底图] 3508×2480       │
│ [x] 奖项      award          │ │  → 自动建议 A4 横向        │
│ [ ] 语种      language       │ │ ┌───────────────────────┐ │
│ [ ] 指导老师  instructor     │ │ │   底图（用户上传）      │ │
│ [ ] 作品名称  work_name      │ │ │   ┌─────────┐          │ │
│ [ ] 证书编号  cert_number    │ │ │   │ 选手姓名 ✥│←拖到位置  │ │
│ …                            │ │ │   └─────────┘          │ │
└──────────────────────────────┘ │ └───────────────────────┘ │
                                 │ 选中：字号 26 对齐居中 颜色 #1a1a1a│
                                 │ [预览真实数据]   [保存]     │
                                 └────────────────────────────┘
```

**一次性工作**：一份模板只需勾选 + 定位一次。之后换数据就能批量出。
**且换底图分辨率不用重定位**（因为存的是百分比）。

#### 7.3.5 匹配方式：按「名字」，不按「位置」

用户还提过一个更省事的设想：**识别模板里的横线，按先后顺序依次对应字段**。
诉求（一份模板 + 自动填充）正确，但**按位置匹配有四个硬伤**：

| 硬伤 | 说明 |
|---|---|
| **顺序是隐式的** | 不同模板字段顺序不同（选手证书"姓名→作品→奖项" vs 指导教师证书"教师→学生→赛事"）。系统凭什么知道第 1 个空是"姓名"还是"教师姓名"？**最终还是要告诉系统顺序 —— 配置没省掉，只是藏起来了，反而更难排查** |
| **"横线"在 Word 里有 5 种表示** | 下划线格式 `w:u` / 制表位前导符 / 连续下划线字符 / 表格底边框 / 绘制的直线 —— XML 表示完全不同 |
| **非字段横线会全盘错位** | 模板里只要有一处"签字：______"，后面所有字段整体错位 |
| **无法处理重复段落** | "一人一页"要复制段落块 N 次，顺序替换做不到 |

**改用命名占位符**：`{{选手姓名}}` 按名字查数据，与顺序无关。
顺序怎么变都不会错位；新增字段不用重排。

**而"横线视觉"天然就有** —— 底图里本来就有横线，HTML 只需把文字打在横线位置上。

#### 7.3.6 字段：从数据库表勾选（不由用户手写）

**字段的完整集合来自工作台的数据库表**，用户在定位器里**勾选**需要的那些：

```
┌─ 可用字段（来自数据库） ──────────────────┐
│  [x] 选手姓名     certificates.player_name │
│  [x] 奖项         certificates.award       │
│  [ ] 语种         certificates.language    │
│  [ ] 指导老师     certificates.instructor  │
│  [ ] 作品名称     certificates.work_name   │
│  [ ] 证书编号     certificates.cert_number │
│  [ ] 组别         certificates.group_name  │
│  [ ] 选送机构     certificates.org_name    │
│  …                                        │
└──────────────────────────────────────────┘
        ↓ 勾选后，每个字段在底图上生成一个可拖拽的框
        ↓ 拖到正确位置 → 调字号/对齐/颜色
```

**字段目录怎么来**：从数据库表的列自动派生（`PRAGMA table_info(<表>)`），
配一份「列名 → 中文标签」的默认映射用于界面显示。**标签可改，只影响显示，不影响取值。**

可选的字段来源表（按打印对象）：
- 证书 → `certificates`（已含 player_name / award / work_name / cert_number / group_name /
  instructor / language / cert_round / org_name / receiving_org 等冗余字段，基本够用）
- 名单 / 报表 → `players` / `organizations` / `projects`

**为什么"勾选"优于"用户手写字段名"**：

| | 手写字段名 | **勾选数据库列** |
|---|---|---|
| 数据绑定 | 要另建"字段名→数据源"映射，易配错 | **天然绑定** |
| 拼写 | 可能写错 → 取不到值 | **不会错** |
| 类型 | 系统不知道 | 系统知道 |

> 这不违背 §1.1「不越权」：系统提供的是**"数据库里有哪些列"这个客观事实**
> （它自己的数据结构）；**勾哪些、怎么排布、字号多大**，全由用户决定。

**关键：取不到值时必须明确提示**，不能静默留空 ——
例如 20 条记录里有 3 条缺"作品名称"，生成前应汇总提示
「3 条记录缺少「作品名称」，是否继续？」。
这正是本项目反复出现的"静默失效"要防的。

#### 7.3.7 底图：用户自己上传

用户上传自己的底图（PNG/JPG）。常见来源：

| 来源 | 做法 |
|---|---|
| 设计软件（PS / AI / Word / PPT）导出的图片 | 直接上传，版式 100% 保真 |
| 已有证书的扫描件 | 扫描后上传 |
| 纯色/简单底 | 也可不上传底图，只放字段（相当于白纸打印） |

> 一期支持 **PNG/JPG**（零新增依赖，尺寸自动读取）。
> PDF 需要前端渲染（引入 pdf.js），作为后续增强。

#### 7.3.8 输出与打印

- **一份 HTML 含 N 个页面块**（一人一页）→ `@media print` → **一次打印整批**
- 需要电子版时：浏览器打印 → **另存为 PDF**
- 生成后可选**落盘归档**（§3.2）：HTML 文本可直接抽取建索引，比 docx 更容易

#### 7.3.9 与「邮件合并」的关系

邮件合并（A 方案）成本更低、零风险，但**每次要手动跑一遍**，且需要模板里配合并域。
若你要的是"**即刻生成、即刻打印**"，**HTML 生成（本方案）更合适**。

`fill_mode` 字段保留 `'html' | 'mailmerge' | 'none'` 三种取值，互不冲突。

### 7.4 变化怎么吸收 —— 提供能力，不替用户做决定

模板会随项目、年份、证书种类变化。**变化分两种性质，代价差十倍**：

| 变化 | 性质 | 吸收方式 |
|---|---|---|
| 主办单位、赛事名称、Logo | **文案** | 底图上直接画死，或做成动态字段 |
| 年份数字、「第 N 届」 | **文案** | 动态字段（`batch` 每批填一次） |
| 证书标题（获奖 / 指导教师 / 组织奖） | **文案** | 动态字段 |
| 横版变竖版、结构差异大 | **结构** | 另建一份模板 |

**在「底图 + 动态字段」的架构下，前三行是免费的** —— 同一份底图，换字段值就覆盖不同场景。

> **这里要克制**：v3–v7 我曾写下"先做一份模板、别造 20 份"的规劝。
> 按 §1.1 的**不越权**原则，这句话**不该由方案来说** ——
> "该建几份模板"是用户的决定。
>
> 系统的正确做法是**把"一份模板够用"做成能力**（底图 + 勾选字段），
> 让用户自然不需要造很多份，而**不是写成规则去限制**。
>
> 归属维度同理：**提供**按项目 / 赛段 / 年份筛选的能力，**用不用、怎么用归用户**。

### 7.5 打印仍须从工作台发起

用户最终是**从工作台发起生成 / 打印**的。
这保证了 §3.1 的前提成立：**系统知道打印了什么、什么时候、关联哪个实体** ——
打印留痕与自动归档才能落地。

若用户完全绕过工作台、直接在 Word 里打印，则拿不到留痕 ——
这是本方案的固有边界，已在 §3.1 说明。

## 8. 打印留痕的价值（不依赖文档量）

浏览界面按「类型 / 时间」聚合：

```
打印记录
  2026-09-30
    14:30  证书 · 省赛获奖证书      20 份   张三、李四…      [查看] [重印]
    14:45  清单 · 选手报名清单      128 条  省赛全部选手     [查看] [重印]
  2026-09-28
```

这解决了**证书分发对账**：寄出去几百张，回头能查"哪天打的、打了谁的、多少份"，
配合现有 `packed` 字段就能对上"打印了但没打包"的缺口。

## 9. 统一搜索

**中文检索策略（基于实测）**：

| 查询长度 | 走哪条路 | 说明 |
|---|---|---|
| ≥3 字 | FTS5 `trigram` MATCH | 快，任意位置子串命中 |
| ≤2 字 | 回退 `LIKE '%词%'` | trigram 对 2 字词恒为 0，**必须回退** |

```python
def search_docs(q: str):
    q = (q or '').strip()
    if not q:
        return []
    if len(q) >= 3:
        rows = db.fetchall(
            "SELECT doc_id, title, doc_type, entity_name, "
            "snippet(doc_index, 4, '<mark>', '</mark>', '…', 20) AS excerpt "
            "FROM doc_index WHERE doc_index MATCH ? ORDER BY rank LIMIT 100", (q,))
        if rows:
            return rows
        # 无结果时也回退一次，避免"看起来没有其实有"
    return db.fetchall(
        "SELECT doc_id, title, doc_type, entity_name, substr(body,1,120) AS excerpt "
        "FROM doc_index WHERE body LIKE ? OR title LIKE ? LIMIT 100",
        (f'%{q}%', f'%{q}%'))
```

**顺带收益**：这同时修掉了「全局搜索在内存里遍历全表」的性能问题 ——
文档搜索走索引，不再全表扫描。

## 10. 分期实施

### 一期：上传底图 + 勾选字段 + 一键出证书

> v9 调整：**模板登记 = 底图 + 勾选的字段**（用户明确的设计）。
> 不再要求登记设计稿文件；源文件路径降为可选项。

1. `print_templates` 表（底图、尺寸、纸张、字段、归属维度，**字段一次建全**）
2. **底图上传**：用户上传自己的 PNG/JPG → **自动读像素尺寸** → **自动建议纸张**
   → 比例不符时提示（§7.3.3）
3. **字段目录接口**：从数据库表的列派生可用字段清单（列名 + 中文标签）
4. **字段定位器**（§7.3.4）：
   - **勾选**需要的字段（来自数据库表，见 §7.3.6）
   - 每个勾中的字段在底图上生成可拖拽的框 → 拖到正确位置
   - 调字号 / 对齐 / 颜色；**预览真实数据**；坐标存百分比
5. **批量生成**：台账选中若干 → 底图 + HTML 叠字 → 一份含 N 页的 HTML → 浏览器打印
6. **生成即归档 + 留痕**（§5.2 / §6）

**验收**：
- 上传底图 → 自动读出尺寸并建议 A4 横向 → 确认
- 从字段目录勾 3 个字段（如 选手姓名 / 奖项 / 证书编号）→ 拖好位置 → 预览正确
- 台账选 5 张证书 → **一键生成** → 打印预览出现 5 页 → 打印 / 另存 PDF
- 打印记录里能查到这次操作，归档目录里有对应 HTML

> **一期的关键是把"即刻生成、即刻打印"跑通** ——
> 上传底图、勾几个字段、选数据、一键出证书，全程不离开工作台。

### 二期：模板多起来之后的组织能力

10. 按项目 / 赛段 / 年份**筛选**模板（归属维度生效）
11. 「另存为副本」—— 版式结构真的不同时，从现有模板复制一份再改
12. 模板与实际打印的**对应关系**提示（"这批证书用的是哪个模板"）

> 这些**字段一期就留好了**，届时只补 UI，不改表。

### 三期：留痕界面 + 全文索引

13. 打印记录界面（按类型 / 时间聚合、查看、重印）
14. `doc_index`（FTS5 trigram）+ `/api/search/docs`（trigram + 2 字回退）
15. 全局搜索合并「数据库记录 + 打印文档」

### 四期：扩展打印对象

16. 报名表、选手清单、签到表、财务报表 —— 复用同一套「登记 + 底图 + 定位 + 生成」机制

### 备选路线：邮件合并

若你更倾向用 Word 原生能力（不引入字段定位），可走 §7.3.9 的邮件合并路线：
导出 xlsx + 一键打开模板，你在 Word 里跑一遍邮件合并。
`fill_mode` 字段已预留，两条路线可共存。

## 12. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| **底图与字段坐标会脱节** | 改了底图（换了版式），原来的字段坐标就对不上了 | 底图 `file_mtime` / 尺寸变化时提示「底图已更新，请复核字段位置」 |
| **图片宽高比 ≠ 纸张宽高比** | 图片被拉伸，整张证书变形 | 上传时**比对比例并明确提示**（§7.3.3④） |
| **打印缩放不是 100%** | 输出整体偏移 | 打印预览页顶部明确提示（§7.3.3⑤） |
| 字段取不到值 | 生成出空白，用户不一定会逐张检查 | **生成前汇总提示**（"3 条记录缺少作品名称，是否继续？"），不静默留空 |
| 归档 HTML 引用底图路径 | 底图移动/删除后归档件打不开 | 底图统一放素材库并纳入备份；归档时校验底图存在 |
| 留痕覆盖不到"绕过工作台直接打印" | 直接在 Word 里打印无记录 | 本方案固有边界，已在 §3.1 说明 |
| 2 字词搜索回退 LIKE | 大量文档时较慢 | 2 字查询结果集通常不大；且仍比现在的全表内存遍历快 |
| `doc_index` 不纳入快照 | 与数据库记录可能不一致 | 提供「重建索引」入口，从 `print_logs` + 归档 HTML 重新抽取 |

> **已消除的风险**：
> - docx 的 **run 分割坑**（v6 换 HTML 后不复存在）
> - **"模板泛滥"不再作为风险列出** —— 那是用户的决定，系统只负责把"一份够用"做成能力（§7.4）
> - **"项目文案没结构化"已删除** —— 该中间层在 v8 被省掉了

## 13. 待确认的决策点

用户已就四项作答（v8）：

| 问题 | 用户答复 |
|---|---|
| 底图怎么来 | **用户自己上传** |
| 字段怎么定 | **动态字段，用户自定义添加**（从证书需要替换的地方来） |
| 项目打印信息字段 | **已包含在前两项里** → §5.5 已删除 |
| 一届有几类证书 | **属用户决策，系统做平台与半自动化，不越权** → §1.1 立为产品原则 |

**因此剩下的待确认项很少了**：

1. **输出形态**：一份含 N 页的 HTML（**一次打印整批**，推荐）
   还是 N 份独立文件（便于逐份归档 / 邮件发送）？
2. **模板登记方式**：约定目录扫描 + 手动添加任意路径，够用吗？
   （按不越权原则，这属于系统能力，默认两者都提供）
3. **打印分组**：按收件机构分批（对齐现有 `groupByReceivingOrg`），还是按项目/赛段整批？
   —— 也可以做成"用户自选"，不预设。
4. **留痕是否记录操作人**：本地单机只有一个用户，记录 `printed_by` 是否有意义？
   （建议保留字段，将来多用户时不用改表）

> **已作废的问题**（不再需要用户回答）：
> - 纸张尺寸、毫米精度、打印校准页 → 版式在底图里，**尺寸自动读取**
> - 模板该有几份、按什么维度组织 → **用户决定**，系统只提供能力（§1.1）
> - 字段清单有哪些 → **用户自定义**，系统不预设（§7.3.6）
> - 项目打印信息字段 → **已删除**（§5.5）

## 14. 现有开源方案调研（是否重复造轮子）

> 用户提问：「类似这种批量化打印系统，GitHub 上有没有？有就可以不用重复造轮子。」
> **结论：有类似的，但没有一个"栈匹配 + 够成熟 + 协议安全"的现成轮子。**
> 建议：**自研为主，但参考/评估 worm-vue3-print**（详见 §14.3）。

### 14.2 一个必须注意的搜索陷阱

GitHub 上搜 **"certificate generator"** 出来的高 star 项目**几乎全是 SSL/TLS 证书**：

- `dakshshah96/local-cert-generator`（971★）→ 本地 HTTPS 证书
- `Fishdrowned/ssl`（537★）→ 自签名通配符 SSL 证书
- `soulteary/certs-maker`（240★）→ 自签名证书工具

**它们和"奖状/荣誉证书"完全不是一回事。** 真正相关的是**「打印模板设计器 / 标签设计」**这一类。
（后续若再调研，请搜 `print template designer` / `label designer`，不要搜 `certificate generator`。）

### 14.3 各候选的具体分析

**worm-vue3-print（最值得评估）**：

- MIT、Vue 3 + TS monorepo、`npm` 已发布 `@worm-vue3-print/core` / `@worm-vue3-print/canvas`
- 能力：可视化拖拽（吸附/对齐/标尺/图层/撤销重做）、`{field.path}` 数据绑定 + 表达式引擎、
  分页排版（`perSheet` 自动分页）、批量打印（`copies`）、**Electron 静默打印**（`webContents.print({ silent: true })`）
- 三端一致：浏览器预览 / Playwright 服务端 PDF / 桌面客户端
- 依赖审计：545 个包逐包核对，无 GPL/AGPL/LGPL（无传染风险）
- ⚠️ 风险：**10 star、创建未满 1 个月**。若作者停止维护，需自己接手
- 在线演示：https://worm-longliu.github.io/worm-vue3-print/

**Foliq（最成熟但最重）**：

- 134★、MIT、4 年历史，架构值得学习（框架无关 core + 渲染组件 + 编辑器三层分离）
- ⚠️ 但 v2 是 **React** 设计器 + **NestJS + PostgreSQL**，与本项目（Vue 3 + Python 标准库 + SQLite + 本地单机）
  **完全不是一套技术栈**；且需要 Docker 部署 PostgreSQL
- ⚠️ README 明确："批量输出/任务队列" 属**roadmap 后续能力**，当前 v1 未包含
- 其 Vue 2 旧版在 `legacy/`，npm 包 `print-template-designer`，**API 与 v2 不兼容**

### 14.4 结论与建议

**不整体替换，但做定向评估。** 理由：

1. **我们的需求已经砍到很薄** —— v4 砍掉自研渲染引擎、v6 换 HTML、v8 删中间层之后，
   剩下的核心只是「**在图片上拖几个字 + 字符串替换 + 循环生成 HTML**」，自研成本可控
2. **现成方案没有刚好合适的** —— 成熟的栈不匹配（Foliq 要 PG+React、gLabels 不可嵌入）；
   栈匹配的都太年轻（10–15 star、1–2 个月）
3. **外部依赖有维护风险** —— 10 star 的项目随时可能停止维护，届时反而更被动

**建议的具体动作**：

1. **先花半天实际试用 worm-vue3-print 的在线演示**，重点确认三点：
   - 能否把**底图铺满页面**（背景图能力）
   - 字段能否**按百分比 / mm 定位**
   - 能否**传入一组数据批量生成 N 页**
2. 若三点都满足 → **直接集成它的 canvas 包**（MIT，可商用），省掉定位器开发
3. 若不满足 → 按本方案自研（工作量已在可控范围）

> **无论哪条路，本方案已确定的架构判断都成立**：
> 底图承载版式、HTML 承载生成、坐标存百分比、字段从数据库表勾选、不越权。
> 这些与用不用第三方库无关。

## 附：为什么先做这一项

在功能规划的候选中（证书套打 / 届次复用 / 数据体检 / 自动备份 / 批量操作），本方案排第一的原因：

- **补的是「用户最终要拿出去的东西」** —— 全系统唯一还没覆盖的输出物
- **是打印留痕与文档索引的前提** —— 不做它，后两者无处附着
- **纯本地能力**，线上系统反而做不好（依赖本机打印机）
- **复用最多**：证书数据、编号规则、分组逻辑、文本提取器全是现成的
