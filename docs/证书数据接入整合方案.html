证书数据接入「个人工作台」整合方案

来源文件：2026中国故事听我说-证书打包分表（按收件机构）副本.xlsx 日期：2026-09-11 状态：方案已定稿 · 待实施
一句话结论：证书数据应作为工作台里新增的一个独立维度（certificates 事实表）接入，用外键反向关联已有的「项目 / 机构 / 选手」，而不是把证书字段塞进现有模型。这样既满足"项目以后要统计这些数据"，又不污染通用的媒体艺术项目/选手结构。

一、决定方案走向的关键约束（已核实）

核对后端持久化链路后发现一个必须正视的事实：

  • 前端 dataService.save() → POST /api/data/save → db.save_all_data(data)。
  • save_all_data 只持久化一张写死的白名单表（projects / organizations / players / finances / config / materialTypes / knowledge / auditLogs …）。
  • load_all_data 是从 SQLite 表读回，不是读 JSON；workbench_data.json 只在"导出"时才写。
推论：若只新建前端 certificates store，证书数据在下次保存/加载时会被静默丢弃——后端没有 certificates 表、也没把它纳入 load/save 白名单。因此本次接入必须改后端（新建表 + 接线），不能零后端改动。做法完全照搬 players / finances 已有的接入模式，风险可控。

二、核心设计：证书是新增维度，不污染现有模型

证书事实表（一行 = 一张证书 = 一个选手）建议字段如下，以「证书编号」为自然主键：

字段来源列说明
certNumber证书编号自然主键（如 【川】CNRCSOV2026xxxx），导入按它去重
projectId（本赛事建一条项目记录）关联「2026 中国故事听我说」
orgName选送机构(校区) / 收件机构始终保留明文，便于核对
orgId同上按机构名匹配现有 organizations，匹配不到则留空
playerName选手姓名
playerId同上按「姓名+机构」软关联 players（不强制生成）
group组别对应现有 player.category
award奖项特金奖 / 金奖 / 银奖 / 铜奖 / 退赛
round赛事阶段省赛 / 国赛
workName作品名称缺则 null + missingWorkName=true（约 893 条）
instructor指导老师
language语种
promotion晋级情况
packed打包核对已打包 / 未打包（人工勾选列，可能不全）
sourceSheet / importId—溯源：来自哪个分表、哪次导入

三、与现有模型的衔接映射

现有实体证书如何衔接是否改现有实体
projects（13 条）本赛事建一条项目记录（type 可加「赛事/语言类」），证书挂 projectId；项目详情展示证书奖项分布否（仅新增一条记录 + 详情页加证书指标卡）

chart.js ^4.4.1已是依赖，证书统计图表直接复用，零新增前端依赖—
xlsx 解析不是依赖，需新增（前端 SheetJS）—

四、导入管线设计

  1. 解析：遍历 102 个机构分表的「逐人明细」区块，UNION 成一张事实表；每个分表名作为 sourceSheet / receivingOrg。
  2. 派生：①总览、②校区统计、④待补清单都由事实表实时计算（与现有 store 里 getProjectStats / getFinanceStats 写法一致），不单独存——改了打包状态，汇总自动跟着变。
  3. 去重：以 certNumber 为唯一键，重复则跳过并标记。
  4. 质量标记：缺作品名 → missingWorkName；退赛 → award='退赛'（统计时单独处理）；打包列空 → packed=null。
  5. 溯源：每次导入写 certificateImports 元数据（源文件名、时间、行数、去重数、缺作品名数）。首次全量导入前确认用「副本.xlsx」还是干净母表。

五、统计与展示落点

  • 新增 CertificatesView.vue（路由 /certificates + 侧边栏「证书管理」）：奖项分布（特金/金/银/铜/退赛）柱状图、省赛 vs 国赛饼图、按机构 TOP 榜、语种分布、打包进度（已打包/未打包/待补作品名）。
  • 项目详情页：对本赛事项目，加「证书奖项构成」指标卡（呼应"项目以后要统计这些数据"）。
  • 机构详情页：加「关联证书数 + 奖项构成」指标。
  • 均用 chart.js（已有）绘制。

六、落地分期

Phase 0｜后端持久化（必须）：db.py 新增 certificates 表 → _create_tables 建表 → 写 _save_certificates / get_all → 在 load_all_data 与 save_all_data 的 sections 各加一行。否则数据存不住。
Phase 1｜导入：certificateImport.js（xlsx 解析 + 归一化 + 预览 + 去重 + 质量标记）+ 导入页/弹窗。
Phase 2｜统计展示：CertificatesView + 图表 + 项目/机构详情证书指标联动。
Phase 3（可选）：选手 upsert，证书硬关联 playerId。

七、必须正视的数据质量风险

  1. 约 893 条缺作品名（④待补清单）——导入时标记，不阻断。
  2. 退赛行混入奖项——图表需单独归类。
  3. ③号表缺失（①→②→④ 跳号）——不要依赖它。
  4. 收件机构 vs 选送机构(校区) 口径混用——需明确映射规则（建议：以「选送机构(校区)」为主键关联，sourceSheet 记录收件机构）。
  5. 打包核对/已打包是人工勾选列——可能不完整，UI 要允许后续手动修正。
  6. 源文件是「副本.xlsx」——母表可能与副本不一致，首次全量导入前建议确认用哪份。
  7. 证书编号重复风险——导入按 certNumber 去重，冲突需人工裁决。
  8. 102 机构 vs 现有 10 机构——自动建机构会污染现有数据，建议默认只存 orgName、不匹配则不建。

八、已确认的方向决策

归属模型

已定独立证书模块 + 建一条项目记录

新增独立 certificates 切片，同时把本赛事建为一条 project 记录并用 projectId 关联。证书页能看统计，项目详情也能看证书奖项分布，且不污染通用项目模型。

选手关联

已定软关联，不自动建选手

证书独立成表，按「姓名+选送机构」与 players 做软匹配展示，匹配不到就只存明文。低风险，先把统计跑通。

导入方式

已定应用内上传解析

前端加 SheetJS(xlsx) 依赖，做「上传→解析→预览→确认导入」闭环。可重复、自助操作，后续更新副本文件能再导。

本方案依据现有代码核实（stores / dataService / db.py 持久化白名单 / package.json 依赖 / router），未改动任何代码。实施前请确认源文件（副本.xlsx 或干净母表）。
