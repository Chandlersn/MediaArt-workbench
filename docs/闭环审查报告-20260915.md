## 一、审查方法

1. **双向抽取接口**：从后端各 `routes.py` 抽取实际处理的 `(方法, 路径)`；从前端 `src/**` 抽取所有 HTTP 调用 `(方法, 路径)`。
2. **逐条比对**：路径 + 方法是否一一对应（不匹配即 404/405 断点）；路由前缀是否会被更早注册的前缀误截。
3. **链路核查**：对每条闭环，核对 `前端入口 → API → 后端处理 → 落库(是否提交) → 回读字段` 五段是否自洽。
4. **权限门核查**：核对接口挂的权限与权限矩阵（`MODULES`/`ROLE_PERMISSIONS`）是否一致。
5. **运行时实证**：对关键结论用真实请求验证，不靠推断。

## 四、断环与风险清单（按严重度）

### F1【高 · 已实证】非 admin 角色的"写入"整体断裂
- **现象**：`editor` 在权限矩阵中拥有 `projects:edit` 等编辑权，但编辑项目后前端调用 `POST /api/data/save`，被 **403** 拒绝——**编辑器/查看者的一切数据修改都不落库**。权限配置页却显示这些角色可编辑。
- **根因**：主写入路径挂的是**遗留权限名**，不在模块枚举内：
  - `resources/routes.py:243`　`@require_permission('manage_config')` → `def save_data`
  - `permissions.py:24`　`MODULES = [projects, organizations, players, finances, users, knowledge, resources, settings]`（无 `manage_config`）
  - `utils/permissions.py:193`　`if module not in MODULES or action not in ACTIONS: return False` → 非 admin 恒 False
- **实证**：
  ```
  viewer POST /api/data/save -> 403 权限不足，需要 manage_config 权限
  editor POST /api/data/save -> 403 权限不足，需要 manage_config 权限
  has_permission('editor','manage_config')   = False   ← 实际门禁
  has_permission('editor','projects','edit') = True    ← 矩阵承诺
  ```
- **性质**：权限矩阵与实际执行**自相矛盾**；当前系统只有 admin 一个账号，故此断环尚未暴露，但一旦增添 editor/viewer 账号即失效（与本轮"增添下属账户"功能直接冲突）。

### F2【高 · 风险】全量保存"先清空再回填"，多数表无空值保护
- **实现**：`db.py:652-671` 对 `projects/organizations/players/finances/certificates` 等执行 `DELETE FROM 表` 后再逐条 `INSERT OR REPLACE`。
- **缺口**：**仅 `certificates` 有空值保护**（`db.py:659` `if label == 'certificates' and not payload: continue`）；`projects/organizations/players/finances` **没有**。
- **后果**：只要某次保存的载荷里该键为空数组，就会**清空整表且不报错**（`success` 仍为 True）。
- **高危组合**：与刚修复的 `dataService.getData()` 无参返回 `[]` 同类问题叠加时，极易出现"加载异常 → 内存快照为空 → 保存 → 清库"。建议对所有 `clear_table` 统一加空值保护。

### F3【中】两套并行的写入实现 + 死路由
- **主路径**：`POST /api/data/save`（全量快照）。
- **并行实现**：`POST/PUT/DELETE /api/projects|organizations|players|finances|knowledge` 这套专用 CRUD 路由，**前端从未调用**（前端仅调用 `/list`；`finances` / `knowledge` 两组路由**完全无调用者**）。
- **证据**：前端调用全量抽取中无上述写路径；各 store 一律 `dataService.setData(...)+save()`。
- **性质**：两套实现并存 → 字段/校验双标、维护成本与认知负担；改动一处不影响另一处，易产生"改了没用"的假象。

### F4【中 · 已实证】备份/恢复/同步同样是"遗留权限名"，非 admin 恒 403
- `resources/routes.py:517` `@require_permission('create')` → `create_backup`
- `resources/routes.py:544` `@require_permission('delete')` → `restore_backup`
- `resources/routes.py:402/447` `@require_permission('manage_config')` → `import_from_json` / `export_to_json`
- 实证：`editor POST /api/data/backup -> 403 需要 create 权限`。
- 与 F1 同源：`create`/`delete` 亦不在 `MODULES`。

### F5【中】系统类接口只校验"已登录"，不校验权限
- 以下接口仅走 `_auth`（任意登录用户，含 viewer 即可执行）：
  - `POST /api/config/archive-path`（改归档目录）
  - `POST /api/config/resources-path`（改资源目录）
  - `POST /api/save-stage-materials`（改归档资料类型配置）
  - `POST /api/cleanup/execute`（清理临时文件）
  - `POST /api/trash/purge-all`（清空回收站）
- 对照：`POST /api/audit-logs/clear` 已做 `settings:delete` 校验（本次新增时加）。
- **性质**：权限粒度不一致；`viewer` 理论上可改系统路径配置。

### F6【低】`/api/status` 无鉴权
- `system/routes.py:111` 该分支不调用 `_auth`。返回运行平台、Python 版本、各表记录数、启动时长。单机自用可接受，属信息暴露。

### F7【低】`archiveMappings` 只读无写
- `db.py:599` 由 `load_all_data` 读取；全项目**无任何写入器**（`_save_archive_mappings` 不存在）。该键恒为空/默认值，属残留字段。

### F8【低】无调用者的后端接口（疑似死路由）
- `GET /api/auth/me`（前端改用 `/api/permissions/me`）
- `finances` / `knowledge` 路由组（前端改走 `/api/data/save`）
- `archive` 侧的 `POST /api/upload`、`DELETE /api/delete-file`（路由表把它们指向 `ResourcesRouter`，archive 内同名实现不可达）

## 附：前端 scoped / 全局 CSS 级联隐患扫描（2026-09-15）

**成因**：CSS 是**逐属性**级联。组件 `<style scoped>` 的 `.foo[data-v-x]` 只覆盖它**声明了**的属性；未声明的属性会被全局 `style.css` 里的同名 `.foo` 补上（全局选择器特异性低，但属性不冲突时就生效）。

**方法**：解析 `style.css` 与所有 `.vue` 的 scoped 块，只取「选择器整体为单个类」的规则（带后代的只在特定父级下生效），**排除 `@media`**（避免窄屏规则误报），比对同名类的**结构属性**差异（display / flex-direction / justify-content / align-items / text-align / position / visibility 等）。

### A. 已确认为真冲突（全局值改变了组件布局，均已修）

| 位置 | 全局规则 | 后果 | 修法 |
|---|---|---|---|
| `GuideView.vue` `.section-header` | `justify-content: space-between` | 图标贴最左、标题被推到最右 | scoped 补 `justify-content: flex-start` |
| `ProjectsView.vue` `.project-card` | `display:flex; justify-content:space-between; align-items:center` | 卡片的 header/body/footer **三个子块被排成一行并两端撑开**（原意纵向堆叠，三者都带 `margin-bottom`） | scoped 补 `display: block` |

### B. 危险陷阱（已清除）

| 规则 | 风险 | 处置 |
|---|---|---|
| `style.css` `.page { display:none !important; visibility:hidden !important }` + `.page.active{...}` | 任何组件只要用 `class="page"` 就会被**强制隐藏**，且 `!important` 使组件难以覆盖 | **已移除**（2026-09-15）。确认依据：① 全项目无元素使用裸 `page` 类（按类名分词严格核对，仅 `:class="{active: page===currentPage}"` 这类**循环变量的表达式文本**，非类名）；② `ProjectFormView` 内那条 `.page{padding:24px}` 是死 CSS，一并移除。备份 `backup_style_css_*` |

### C. 共享基础样式（全局有意提供，泄漏即设计，非问题）

以下同名类是全局**故意**提供的基础布局，各组件不重复声明属正常，共约 100 处：

`.btn-primary` / `.btn-secondary` / `.btn-danger`（inline-flex + 居中）、`.form-group`、`.modal-body`、`.modal-close`、`.empty-state`（text-align:center）、`.page-header`（flex space-between）、`.detail-content`、`.chart-card`、`.stat-card`、`.stat-icon`、`.icon-btn`、`.form-hint`、`.header-actions`、`.filter-select`（height:36）、`.radio-group`、`.project-list`（本组件用 grid，flex-direction 无碍）等。

**判据**：全局规则若是为**同一用途**提供基础样式（按钮/表单/弹窗/空态），则泄漏是预期；若是**同名但不同用途**（如 `.section-header` 的两处语义不同），则是 bug。

## 六、可复用的审查手法

- **先比接口，再比权限，最后比数据**：接口清单双向 diff 能在几分钟内排除 404/405 类断点；剩下的问题几乎都藏在"权限门"与"落库写法"里。
- **"出现 403 的提示里带着一个不在模块列表中的名字"** 是遗留权限的强信号（本例 `manage_config`）。
- **凡"先 DELETE 再 INSERT"的全量保存**，一律先问：空载荷会怎样？
