## 二、严重问题（已实测复现）

### S1. 任意文件下载 — 静态目录回退到项目根

`server.py:97-116`：dist 不存在时 `STATIC_DIR = BASE_DIR`，`do_GET` 末尾 `super().do_GET()` 兜底，把整个项目目录（含 `data/`、`server.py`、`node_modules/`）发布出去。

实测（dist 未构建时）：

```
GET /data/jwt_config.json     -> 200  {"secret_key": "IYoYY4rtvGu1UHbSt..."}
GET /data/workbench_data.json -> 200  34702 字节全量业务数据
GET /server.py                -> 200  后端源码
GET /data/workbench.db        -> 200  SQLite 数据库文件
```

触发条件：`启动工作台.bat` 在 dist 未构建时启动。构建 dist 后本漏洞消失（已复测 404）。

### S2. 任意文件读取 — 路径未约束（持续存在，与 dist 无关）

`server.py:1606 serve_file()`、`:1572 open_file()`：仅 `os.path.join` + `normpath`，无 `realpath` 白名单校验，且接口**无认证**。

实测：

```
GET /api/get-file?path=C:/Windows/win.ini        -> 200（读出系统文件）
GET /api/get-file?path=../data/jwt_config.json   -> 200（读出 JWT 密钥）
GET /api/get-file?path=../../../Windows/win.ini  -> 404（跳过了项目根，边界随机）
```

危害：匿名者可读取服务器任意有权限的文件；`open_file` 还会 `os.startfile()`，可诱导服务端启动本地程序。

### S3. 用户管理 API 完全无认证，泄露密码哈希

`server.py:3139 get_users()` / `:3159 add_user()` / `:3195 update_user()` / `:3221 delete_user()` 均无 `_check_auth_and_permission`。

实测：

```
GET /api/users -> 200
{"success":true,"users":[{"id":"u1774154968201","username":"admin",
 "password":"JDJiJDEyJEhnelltbHpTVUsvREouTnN2...",  "role":"admin", ...}]}
```

- 匿名获得 admin 的 bcrypt 哈希（可离线爆破）
- `add_user` 无认证可写入垃圾用户；`update_user:3201` 用 `{**u, **data}` 全量合并，无字段白名单
- 缓解：server.py 未定义 `do_PUT`（实测 PUT 全部 501），所以 update_user / rename-folder 实际不可达；但 GET 泄露与 POST 写入**可达**

### S4. 未认证写操作（"允许未认证访问"模式）

`server.py:861-873 create_folder`、`:898-907 save_file`、`:909-922 copy_to_archive`、`:941-948 backup`，注释明确写着"尝试认证，但允许未认证访问"。

实测：

```
POST /api/create-folder {"path":"_sec_test"}  -> 200
{"success":true,"path":"D:\...\MediaArt_Archives\_sec_test"}   # 目录已真实创建（已清理）
```

危害：匿名者可任意上传文件、创建目录、写入归档区。

### S5. 目录遍历 API 无认证

`server.py:4260 browse_directories()` 无鉴权，可枚举服务器任意目录：

```
GET /api/browse-dirs?path=C:/ -> 200
{"directories":["$Recycle.Bin","Program Files","Users","Windows",...]}
```

同类无认证接口：`/api/audit-logs`（3048）、`/api/notifications`（4425）、`/api/import-players`、`/api/cleanup/scan`、`/api/cleanup/execute`。

### S6. JWT 密钥明文落盘且可被下载

`data/jwt_config.json` 明文存储 `secret_key`。配合 S1/S2 可匿名获取 → 可自签任意角色 token，完全绕过 RBAC。

### 9.1 用户报告的现象

### 9.4 严重：一条脏数据会让整张库回滚（本轮最重要的隐患）

运行日志中捕获到：

```
sqlite3.IntegrityError: NOT NULL constraint failed: users.username
  server/database/db.py:494 _upsert  ←  db.py:545 _save_users  ←  db.py:436 save_all_data
```

**根因链**：

1. `server.py::add_user` 构造的记录只有 `name`，**既无 `username` 也无 `password`**；
2. 而 `schema.sql:94-105` 规定 `users.username TEXT UNIQUE NOT NULL`、`password TEXT NOT NULL`；
3. `save_all_data()` 把 11 张表的读写放在**同一个事务**里，任一条记录抛异常 → 整个事务 `rollback()`。

**后果**：点一次"新增用户"，不仅用户进不了库，**其他所有表当次的写入也全部作废**；而读取时 SQLite 优先，于是 JSON 有、库没有，重启后数据"凭空消失"。

**修复分三层**：

| 层 | 文件 | 措施 |
|---|---|---|
| 记录级 | `db.py::_upsert` | 捕获 `IntegrityError`，跳过该条并打印 `表名 + id + 原因`，不再向上抛 |
| 表级 | `db.py::save_all_data` | 各表独立 `try/except`，单表失败不影响其他表；失败清单汇总打印并返回 `False` |
| 账号级 | `db.py::_save_users` | 先过滤缺 `username`/`password` 的记录；若全部不合法则**放弃本次同步、保留现有账号**，绝不整表清空 |

### 9.5 同批次发现："只删不写"导致的数据丢失隐患

`save_all_data()` 原本无条件执行 11 条 `DELETE FROM`，但其中 **`templates` 和 `audit_logs` 根本没有对应的写入函数**（`_save_templates` / `_save_audit_logs` 不存在，`_save_*` 清单里只有 10 个）。等于**每次保存都把这两张表清空一次**，而 `load_all_data()` 又依赖它们读出模板与审计日志。

**修复**：

- 新增 `_save_templates()`（结构同 `_save_knowledge`，类型取自外层 dict 的 key）与 `_save_audit_logs()`；
- 把"先清空"动作统一下沉到各自 `_save_*` 内部，且只在该表本次确实要回填时才执行 —— 从机制上杜绝"删了却没有数据可写"；
- `_save_audit_logs()` 额外加保护：本次提交为空、而库中已有记录时跳过清空，避免前端拿过期快照回写就抹掉审计轨迹。

> 注：`checklists` 表既无清洗也无写入器，前端 checklist store 在数据缺失时会自行重建默认结构，故本轮未强行接入（形状未定，贸然落库风险更大）。

### 9.6 用户模块：新增即完整账号、角色改得动

| 问题 | 位置 | 修复 |
|---|---|---|
| 新增用户不成其为账号（无登录名/密码） | `server.py::add_user` | 缺 `username` 时由邮箱前缀或姓名派生并保证唯一；缺 `password` 时生成 10 位随机初始密码，bcrypt 加密入库，**仅一次**回传 `initialPassword`；`name` 与 `realName` 双写；角色按 `ROLE_PERMISSIONS` 白名单校验 |

## 十、本地文件预览功能评估（2026-09-10）

### 10.1 结论

**UI 做完了，链路基本没通。** 预览面板本身（6 类格式分支、下载按钮、滑入动效、样式）是完整的，但真正把文件喂给浏览器的那一步几乎全线失败：媒体类在浏览器里 **100% 打不开**，选手/项目的素材连文件都定位不到。

按"能不能看到内容"分档：

| 场景 | 实际结果 | 依据 |
|---|---|---|
| 图片 / 视频 / 音频 / PDF（三个详情页） | **完全不可用** | 媒体 URL 无 token → HTTP 401 |
| 选手素材（任意格式） | **完全不可用** | 服务端定位返回 404 |
| 项目资料（任意格式） | **完全不可用** | 服务端定位返回 404 |
| 机构资料的 **docx/xlsx/pptx** | **可用** | 实测提取 1387 字符可读正文 |
| 机构资料的 **媒体**（图片/PDF/视频） | **不可用** | 服务端能定位（200），但浏览器加载时 401 |
| 纯文本类（txt/md/csv/json/log/html…） | **不可用** | 前端声明可预览，后端不支持提取，固定返回 400 |
| `.doc`（旧版二进制 Word） | **输出乱码** | 走 BadZipFile 兜底，返回文件前 8KB 原始字节 |

### 10.2 P0-A：媒体预览的 URL 不带凭证 → 401（最致命）

**现象**：三个详情页把服务端 URL 直接塞进 HTML 元素 —— `<img :src>` / `<iframe :src>` / `<video :src>` / `<audio :src>` / `<a :href download>`。这类"元素级"请求**浏览器不会附带 `Authorization` 头**，而 `/api/download-player-material`、`/api/download-project-material`、`/api/get-org-material` 都不在 `PUBLIC_API_EXACT` 白名单（server.py:280-287）里，统一认证门禁（server.py:405）直接拦掉。

**实测**：

```
不带 token  /api/download-player-material  → 401
不带 token  /api/preview-text              → 401
不带 token  /api/get-org-material          → 401
带   token  /api/get-org-material          → 200  (application/pdf)
```

**为什么文本/Office 预览反而没事**：它是走 `get(textUrl)` 发起的，请求封装会自动带上 header。所以同一张预览面板里，"文字能看、图片看不了"，成因就是这个。

**连带影响**：面板右上角的下载按钮（`<a :href="url" download>`）同样是 401 —— 用户点下载，拿到的是一个 JSON 错误页而不是文件。

### 10.3 P0-B：选手 / 项目素材定位不到文件 → 404

`ARCHIVES_DIR` 下的资料是**按类型分子目录**存放的，例如：

```
MediaArt_Archives/02_选手档案/周小杰/02_参赛历程/周小杰_初赛_作品介绍_5635.doc
MediaArt_Archives/01_项目资料/2026年春季艺术展演/01_策划文档/....docx
```

而路径解析器 `_resolve_material_candidate()`（server.py:321）在**没有传 `material_type` 且未开启 `allow_subdir_search`** 时，只会尝试 `base/文件名` —— 必然找不到，返回 404。

关键在于三个来源的支持度不一致（同一份 UI 复制三份，改的时候没对齐）：

| 来源 | 服务端是否读取 `materialType` | 是否开子目录搜索 | 前端 URL 是否带 `materialType` | 结果 |
|---|---|---|---|---|
| 机构 `preview_file_text('org')` | ✅ (server.py:2731) | ✅ | ✅（OrganizationDetailView:403） | **能定位** |
| 选手 `preview_file_text('player')` | ❌ (server.py:2732) | ❌ | ❌（PlayerDetailView:630/648） | **404** |
| 项目 `preview_file_text('project')` | ❌ (server.py:2733) | ❌ | ❌（ProjectDetailView:489） | **404** |

而且 `/api/download-player-material`（server.py:635-642）与 `/api/download-project-material`（661-667）**连 `materialType` 参数都没读**，所以前端就算传了也白传。

**附带**：这两个端点也没读 `preview` 参数，`download_player_material(..., preview=False)` 默认走 `Content-Disposition: attachment`；机构那条走 `download_org_material(..., preview=True)` 才是 `inline`。同一功能两种行为。

**实测**：

```
带 token  /api/preview-text?source=player&...                          → 404 文件不存在
带 token  /api/download-project-material?...（前端原样 URL）            → 404 文件不存在
带 token  /api/preview-text?source=org&...&materialType=01_合作协议     → 200  1387 字符
```

### 10.4 P1-A：PDF 文本提取是死代码（当前被 UI 绕过，但 `.doc` 会暴露）

`extract_office_text()`（server.py:2645）用 `zipfile.ZipFile(file_path)` 打开文件，**PDF 不是 ZIP**，所以还没走到 `.pdf` 分支（2695-2703，本想用正则抠文本）就已经抛 `BadZipFile`，落进兜底分支（2707-2713）——**返回文件前 8192 字节解码结果**。

**实测**（直接调接口）：

```
/api/preview-text?source=org&...&materialType=往来函件 (PDF)
→ {"success": true, "text": "%PDF-1.6\n%äüöß\n2 0 obj\n<</Length 3 0 R/Filter/FlateDecode>>\nstream\n..."}
```

**目前为什么没炸到用户**：前端只在 `isText || isOffice` 时才调文本提取，PDF 走的是 `isPdf` 的 `<iframe>` 分支 —— 所以这段坏逻辑现在是**不可达的坏代码**（但 401 修好后要小心别把它接回来）。

**真正会暴露的是 `.doc`**：`.doc` 在 `office_exts` 里 → 走文本提取 → 旧版二进制 Word 也不是 ZIP → 同样落到兜底分支 → **预览面板里显示 8KB 乱码**（归档里真有 `周小杰_初赛_作品介绍_5635.doc`）。

前端 `textExts` 声明了 `txt/md/json/xml/csv/log/html/css/js/ts` 十种可文本预览，但 `preview_file_text()` 只处理 Office + PDF（server.py:2756），其余一律：

### 10.7 修复建议（按性价比排序）

1. **先修凭证传递（P0-A）**，三选一：
   - **A｜Blob 拉取（推荐）**：`get()` 取回二进制 → `URL.createObjectURL(blob)` 交给 `img/video/audio/iframe`，关闭时 `revokeObjectURL`。token 仍走 header，不落地、不进日志；代价是视频先整段下载、不能边下边播（本地桌面场景可接受）。
   - **B｜短期票据**：新增 `/api/preview-ticket` 换一个限文件、几十秒过期的一次性票据，再用 `?ticket=` 加载。最安全，但要加接口。
   - **C｜查询串带 token**：改动最小，支持 Range/流式播放；但 token 会进 URL、日志与浏览器历史，**削弱了之前刚加固的鉴权**，不推荐。
   - ⚠️ 不要把 `/api/download-*` 加进公开白名单 —— 那等于把任意文件读取重新打开。
2. **再修定位（P0-B）**：`/api/download-*-material` 读 `materialType` 并透传；`preview_file_text` 的 player/project 分支补 `allow_subdir_search=True`；前端三个 URL 统一带上 `materialType` 与 `preview=true`。
3. **纯文本（P1-B）**：`preview_file_text` 加纯文本分支，做多编码尝试（utf-8 → gbk → latin-1，`errors='replace'`）。
4. **`.doc`（P1-A）**：识别后提示"不支持在线预览，请下载"，别再输出乱码字节。
5. **工程（P2）**：把预览面板抽成一个 `FilePreviewPanel.vue` 组件（props: url/name/type），三个详情页 + 素材库 + 归档复用；顺手补 Esc 关闭与图片缩放。

### 10.11 追加：继续排查后的第三批（用户"继续完善"）

沿用 10.10 的两个静态扫描思路继续深挖，又发现 4 个"构建期不报错、运行时才炸/功能静默失效"的问题。

#### A. `targetPath` 从未在后端实现 —— 三处上传全部落错目录

前端有三个页面都在用 `targetPath` 指定目标目录，但 `upload_resource()` 的 multipart 解析只读 `filename`/`folder`/`orgName`/`materialType`，**`targetPath` 一个字都没读**，于是所有上传都落到素材根目录：

| 页面 | 期望落点 | 实际落点（修复前） |
|---|---|---|
| ResourcesView（素材库·按分类上传） | `RESOURCES_DIR/<分类文件夹>` | `RESOURCES_DIR` 根 |
| ArchiveView（归档页·上传到当前目录） | `ARCHIVES_DIR/<当前路径>` | `RESOURCES_DIR` 根 |
| TemplatesView（模板页） | `RESOURCES_DIR/templates` | `RESOURCES_DIR` 根 |

**修复**：`upload_resource()` 解析 `targetPath`，以 `ARCHIVE_TOP_DIRS` 前缀区分基准目录（归档 → `ARCHIVES_DIR`，其余 → `RESOURCES_DIR`），统一走 `_resolve_safe_path` 做越界校验，返回的 `path` 也带上 `targetPath`。

#### B. `TemplatesView` 下载模板 401

`downloadTemplate` 用 `window.open('/api/get-file?path=templates/<file>')` —— 与 10.10 的素材库下载同一类问题（新窗口请求不带 `Authorization` 头）。改为 `getBlob` + 临时 `<a download>`。注意：A 修好之前，即便 401 解决了也仍是 404（文件根本没落在 `templates/`）。

#### C. 模板元数据前后端结构不一致 —— 上传后刷新即消失

- 后端 `_load_templates()` 返回 `{"contracts": [], "forms": []}`
- 前端读写的是 `{"categories": [...], "items": [...]}`，且字段（`categoryId` / `fileName` / `size` / `icon`）超出 `templates` 表列定义

结果：上传模板时前端 push 进本地数组、`saveTemplates()` 写进 JSON，但重新加载走 DB 的 `_load_templates()` 拿回一个完全不同的结构 → 模板列表永远为空。

**修复**：把整个 `templates` 对象以 JSON 存进 `settings` 表（与 `config` 同一种存法，避免为几个字段改表结构），`_load_templates()` 返回 `{categories, items}`。

> **踩到的坑**：`settings` 读取时会经 `Model._deserialize`，以 `{`/`[` 开头的字符串**已经被解析成对象**，此时再 `json.loads()` 会抛 `TypeError`。第一版把异常吞掉后静默返回空，表现为"写入成功、读出来还是空"（settings 表和 JSON 里都明明有值）。最终对齐 `_load_config` / `_load_archive_config` 的既有写法：`try: json.loads(...) except: 用原值`。

#### D. 另外三处未声明标识符（同 10.10 的 `post` 同一类）

用 espree 解析全部 `<script setup>` 做了一次真正的 `no-undef` 扫描，又查出：

| 位置 | 问题 | 影响 |
|---|---|---|
| `components/LoginModal.vue` | `post` 未导入 | **首次登录强制改密**这条路一进去就抛 `ReferenceError` |
| `views/FinanceFormView.vue` | `Message` 未定义（3 处） | 校验失败/保存出错时抛异常，用户看不到任何提示 |
| `views/OrganizationFormView.vue` | `Message` 未定义（2 处） | 同上 |

`Message` 不存在这样的全局；项目里对应的是 `useMessage()` 组合式函数（`components/Message.vue` 就是用它驱动的），已改为 `const { warning, success, error } = useMessage()`。

顺带修正扫描器的两处误报：`undefined` 是字面量型全局；`__APP_VERSION__` 是 `vite.config.js` 里 `define` 注入的编译期常量。

### 10.12 追加：把一次性排查工具沉淀为项目可复用脚本（第四批）

#### A. 参数契约扫描 → `scripts/check-params.mjs`

思路来自 `targetPath`：**前端约定了一个参数，后端从未读取**。这类问题不报错、不抛异常，只是功能静默失效。

做法：扫描前端所有 http 调用提取（路径 + 参数名），扫 `server.py` 路由守卫建立「路径 → 处理方法」映射，收集处理函数真正读取过的参数名，做差集。

**本轮结果**：全项目 38 个前端 API 路径全部匹配到后端处理函数（覆盖面自检 38/38），只检出 1 处线索——`/api/count-files` 的 `recursive` 前端传了后端没读。核查后确认**无害**：`count_files_recursive()` 本来就是递归统计，该参数是历史遗留。`targetPath` 那类真问题已在前一轮修净。

> 脚本开发中修掉两个自身 bug，值得记下来：
> 1. **固定 N 行窗口会"吃掉"后续路由**：先前用「匹配行 + 后 14 行」切分发块，前面的块会把后面路由的 `if` 行吞进自己的窗口，`matchAll` 非重叠 → 那些路由永远登记不上（覆盖率掉到 19/38）。改为**先定位所有路由守卫位置，再按相邻边界切分**。
> 2. **分发块可能对应多个处理函数**：`/api/import-players` 按 Content-Type 走 `import_players()`（multipart）或 `import_players_json(data)`（JSON），只取第一个调用会误报。改为收集块内全部 `self.xxx(` 调用。

#### B. 前端静态检查 → `scripts/check-static.mjs`

把 10.10 / 10.11 那两次一次性扫描合并固化，检查三项：

| 检查 | 说明 |
|---|---|
| 未声明标识符 | espree 解析 `<script setup>`，做真正的 `no-undef` |
| 缺少导入 | 调用了 `services/http.js` 的封装函数但没 import |
| 模板处理器未定义 | `@click` 等引用了但 `<script setup>` 中不存在 |

零新依赖（espree 9.6.1 由 eslint 自带）。**当前全项目 59 个文件干净。**

> 开发中修掉的误报，都是"看起来像引用、其实不是"的情况：
> - `export { X } from './y'` 转发导出 → 不是本地引用；
> - `export { getUserInfo as getCurrentUser }` 里的 `getCurrentUser` 是**导出别名**（`specifier.exported`），永远不是引用；
> - 内联表达式 `@click="showLogin = true"` 里的 `true/false/null` 是字面量不是标识符；
> - `{ foo: 1 }` 的 key、`obj.foo` 的属性名不算引用。
> - 另外 `import.meta.url` 的 `pathname` 在 Windows 下是 URL 编码的，中文路径会变成 `%E4%B8%AA...`，必须用 `fileURLToPath`。

**自检验证**（关键：一个永远不报错的检查器等于没有）：临时放一个含三类问题的 `src/_check_selftest.vue`，脚本准确报出 4 处（未声明 2 + 缺导入 1 + 模板处理器 1），删除后恢复干净。

#### A. 9 处真 TypeError：错误处理里反而抛错

### 10.15 更正：10.11 / 10.13 里的「1.7 万条样式告警」是我的配置错误造成的幻影数字

#### A. 错在哪

- **降级规则的等级时，必须原样保留选项**。`rules[k] = 'warn'` 会把 `["error", "single"]` 的选项一起吃掉、静默变成默认值——**不报错、不影响构建，但检查标准全变了**，且产生的数字看起来「很合理」（上万条排版告警，像是一个不守规矩的代码库），极具误导性。

浏览器子文件夹的模板里**本来就有** `has-files` 绑定（`item.type === 'folder' && item.fileCount > 0`，`updateFolderCounts()` 早已在统计每个文件夹的文件数），**但 CSS 只有一道 3px 左边框，太弱、几乎看不出来**。已增强为：绿色底（`--success-light`）+ 全绿 inset 边框 + 左侧 3px 竖条 + 文件名变绿加粗。

分类卡片本质上也是文件夹，一并处理：新增 `categoryHasFiles` 响应式 map，在 `fetchCategoryCounts()` 里按 `result.files > 0` 赋值，卡片加 `:class="{ 'has-files': categoryHasFiles[cat.id] }"` 与相同样式，计数文字也变绿加粗。

> **CSS 的一个坑**：`.has-files` 必须写在 `:hover` **之后**。`.item.has-files` 与 `.item:hover` 特异性相同（都是两个类 / 一个类+一个伪类），靠源码顺序分胜负；写在前面会被 hover 的灰底覆盖，绿色就"时有时无"。
