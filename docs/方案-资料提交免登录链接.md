# 方案：资料提交免登录链接

> 版本：v1（待评审）
> 日期：2026-09-29
> 状态：方案阶段，未开始实施

---

## 1. 要解决的问题

README 开篇列的第一个痛点：

> 选手资料散在微信、邮箱、U 盘里，每次要交材料都得一封封催、一个个对

系统目前解决的是**"对"**（检测谁缺什么、缺料置顶），但没有解决**"催"和"交"**——
选手/机构没有入口自己提交，组织方仍然要：

1. 在微信里挨个通知；
2. 收到文件后手工重命名、手工归到对应目录；
3. 再回系统里核对是否交齐。

**本方案补的就是这一段的最后一公里**：给每个选手/机构一条专属链接，对方自己上传，
文件直接落到归档的正确位置，系统里的缺料状态随之自动变绿。

## 2. 现状（已具备的能力 / 缺口）

### 已有，可直接复用

| 能力 | 位置 | 复用来做什么 |
|---|---|---|
| 归档分类权威定义 | `server/archive/taxonomy.py` | 决定文件落到哪个三级目录 |
| 资料类型 → 目录映射 | `resolve_subdir_for_type()` | 把"策划文档"解析成 `01_策划文档` |
| 资料落位与命名 | `server/resources/routes.py` | `_safe_under()` / `_compose_filename()` |
| 归档目录扫描 | `/api/scan-player-files` | **缺料检测的数据来源** |
| 缺料计算 | `src/stores/player.js` `calculateMissingMaterials()` | 判断"已交/未交" |
| 回收站 | `server/utils/trash.py` | 误交文件可恢复 |

### 关键发现：缺料检测是"扫文件系统"的

`calculateMissingMaterials()` 判断某人交没交，靠的是调用
`/api/scan-player-files?name=<姓名>` **扫描归档目录**，而不是查数据库里某张"已交清单"表。

**这带来一个非常好的性质：**

> 只要提交的文件落到 `<归档>/02_选手档案/<姓名>/<类型目录>/` 下，
> 缺料状态就会自动变绿——**前端缺料逻辑一行都不用改。**

这是本方案成本低、风险小的核心原因。

### 缺口

- 没有对外入口（所有接口都要 JWT）
- 没有"提交链接"这个概念的数据模型
- 没有免登录场景下的安全边界（限流、越权、文件校验）

## 4. 数据模型

新增一张表，**刻意不纳入前端全量快照**（理由见 §7.3）：

```sql
CREATE TABLE IF NOT EXISTS submit_links (
    token          TEXT PRIMARY KEY,   -- secrets.token_urlsafe(32)，约 43 字符
    entity_type    TEXT NOT NULL,      -- 'player' | 'org' | 'project'
    entity_id      TEXT NOT NULL,
    entity_name    TEXT NOT NULL,      -- 冗余存储，列表展示用（实体改名后仍可追溯）
    stage          TEXT,               -- 选手赛段，决定要求交哪些资料
    required_types TEXT,               -- JSON 数组：本次要求提交的资料类型名
    expires_at     TEXT,               -- ISO 时间，过期即失效
    max_uses       INTEGER DEFAULT 0,  -- 0 = 不限次（允许重传/补交）
    used_count     INTEGER DEFAULT 0,
    revoked        INTEGER DEFAULT 0,  -- 撤销标记
    created_by     TEXT,               -- 创建人 user_id
    created_at     TEXT,
    updated_at     TEXT
);

CREATE INDEX IF NOT EXISTS idx_submit_links_entity
    ON submit_links(entity_type, entity_id);
```

**为什么用独立表而不是塞进 `settings` / `config` JSON：**

1. 需要按 `token` 精确查询，独立表 + 主键更直接；
2. 数据由**服务端独占生成**，前端不应持有或改写（安全考量）；
3. 不参与全量快照，因此不会被 `POST /api/data/save` 的逐表覆盖误伤。

## 5. 接口设计

### 5.1 管理端（需登录 + 权限）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| POST | `/api/submit-links` | `players:edit` | 生成链接，返回 token 与完整 URL |
| GET | `/api/submit-links` | `players:view` | 列表（可按 entityType / entityId 过滤） |
| DELETE | `/api/submit-links/<token>` | `players:edit` | 撤销（软撤销，置 `revoked=1`） |
| POST | `/api/submit-links/<token>/remind` | `players:edit` | 触发提醒（三期，接通知模块） |

生成请求体：

```json
{
  "entityType": "player",
  "entityId": "p-123",
  "expiresInDays": 7
}
```

`required_types` 由服务端根据 `config.stageMaterials[stage]` 自动推导，
不由前端传入——避免前端构造出与配置不一致的要求清单。

### 5.2 公开端（免登录，仅凭 token）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/public/submit/<token>` | 返回该实体需要提交的清单与已交状态 |
| POST | `/api/public/submit/<token>` | multipart 上传一个文件 |

GET 响应示例：

```json
{
  "success": true,
  "entityName": "张三",
  "entityType": "player",
  "stage": "省级展演",
  "expiresAt": "2026-10-06T20:30:00",
  "items": [
    { "name": "个人信息", "icon": "🪪", "done": false },
    { "name": "作品",     "icon": "🎭", "done": true  },
    { "name": "获奖证书", "icon": "🏅", "done": false }
  ]
}
```

`done` 由服务端扫描归档实时计算（复用 `scan-player-files` 的定位逻辑），
因此**不依赖前端上报，无法伪造**。

POST 表单字段：`file`（文件）、`materialType`（资料类型名）。
落盘目录与文件名由服务端按 taxonomy 推导，**前端不参与路径构造**。

### 5.3 路由注册

在 `server/api/router.py` 新增一条前缀映射：

```python
from server.submit.routes import SubmitRouter
self._submit_router = SubmitRouter()
self.routes['/api/submit-links'] = self._submit_router
self.routes['/api/public/submit'] = self._submit_router
```

公开端**不走 `require_auth`**，由 `SubmitRouter` 内部自行做 token 校验。

## 6. 前端设计

### 6.1 选手端提交页（新增，独立路由）

- 路由：`/#/submit/:token`
- **路由守卫无需改动**：`src/router/index.js` 的 `beforeEach` 只拦截
  `meta.requiresAuth` 的路由，新路由不加这个标记即自动放行。
- **但需要让页面脱离后台外壳**：`src/App.vue` 目前**无条件**渲染
  `<nav class="sidebar">` 与 `<LoginModal>`（第 35、178 行），
  公开页若走同一外壳会显示后台侧边栏，体验不对。
  改法：给公开路由加 `meta: { public: true }`，
  在 App.vue 用 `v-if` 包住后台框架，公开路由时只渲染 `<router-view>`。
  这是本方案对现有前端**唯一一处结构性改动**（约 10 行）。
- 独立轻量布局，移动端优先——对方多半用手机打开
- 交互：清单式，逐项上传，已交项置灰打勾
- 上传后即时刷新该项状态
- 过期/撤销时展示明确的失效提示

### 6.2 管理端入口（改动小）

一期先放在 **选手详情页**：加一个「生成提交链接」按钮 → 弹窗展示链接 + 复制按钮。
二期再做独立的「资料催收」页，支持按项目/赛段批量生成、批量导出链接。

## 7. 安全设计

因为开了一个**免登录写入入口**，这是本方案风险最集中的地方，逐条说明。

### 7.1 身份：token 不可枚举

`secrets.token_urlsafe(32)` ≈ 256 bit 熵，配合限流，暴力枚举不可行。

### 7.2 越权：路径严格锁定

token 只能写入它绑定的实体目录，落盘路径全部经 `_safe_under()` 二次校验：

```
<归档>/<一级分类>/<实体名>/<类型目录>/<文件>
```

实体名、类型目录均来自**服务端从数据库/taxonomy 解析**，不接受前端传路径。
（复用 `_sanitize_filename()` 清洗文件名，防 `../` 穿越。）

### 7.3 只写不读

- GET 只返回"该交什么"，**不返回已交文件的内容或列表**
- 无法通过 token 列举其他人的任何数据
- token 与实体一一绑定，不能跨实体操作

### 7.4 文件校验

| 项 | 策略 |
|---|---|
| 扩展名 | 白名单（图片 / 音视频 / 文档 / 压缩包），拒绝可执行文件 |
| 大小 | 单文件上限，默认 50MB（可配置） |
| 文件名 | `_sanitize_filename()` 清洗，防止路径注入与非法字符 |
| 数量 | 单次请求只接受一个文件 |

### 7.5 限流与滥用防护

- 按 token 限速（如 20 次/小时）
- 按 IP 限速（如 60 次/小时）
- 复用 `server/config.py` 中已有的限流配置风格（`LOGIN_MAX_ATTEMPTS` / `LOGIN_WINDOW_SECONDS`）

### 7.6 过期与撤销

- `expires_at` 到期即失效
- 支持随时软撤销（`revoked=1`），不物理删除记录，保留审计线索

### 7.7 审计

每次提交写 `audit_logs`，**由服务端生成**（记录 token、实体、文件名、IP、时间）。
注意：现有审计日志是前端 payload 携带的，可信度弱；本模块的提交记录走服务端直接写入，
不受此限制。

## 11. 风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| 免登录入口被滥用 | 垃圾文件 / 塞满磁盘 | token 熵 + 限流 + 类型白名单 + 大小上限 + 过期 |
| 链接被转发给他人 | 他人可向该选手目录提交 | 影响可控（只能写这一个实体）；如需更严可加短信验证码 |
| 主办方不知道谁交了什么 | 无法追溯 | 二期补提交记录 + 审计日志 |
| 与全量快照写入模型冲突 | token 被前端覆盖 | 独立表 + 不纳入快照（已设计） |
| 手机端兼容性 | 对方打不开 / 传不了 | 提交页移动端优先、独立轻量布局 |

## 附：为什么先做这个

在功能规划的四个方向里（资料提交链接 / 评分评审 / 通知触达 / 证书套打），
本方案排第一的原因：

- **补的是已声明流程的空缺**（检查清单里"报名登记"目前只有勾选框），用户不需要学新概念
- **复用现有能力最多**（落位、命名、扫描、缺料检测全部现成）
- **对现有代码侵入最小**（主要改动集中在新模块）
- **直接命中产品第一痛点**（资料催收）

⚠️ 需要说明：若后续要做**评分/评审**模块，建议先给写入模型加乐观锁——
评分是并发写入最密集的场景，会直接撞上当前"全量快照覆盖"的 last-write-wins 缺陷。
但**本方案不受此限制**，因为提交链接的数据独立于快照、且写入是单文件追加式。
